# Changelog

See https://docs.meshery.io/project/releases

## Unreleased

- **RTK Cloud client, fix**: the Cloud base query's `prepareHeaders` no longer replaces an `X-Current-Orgid` the endpoint was called with. It sets the selected organization (`state.organization.value.id`) only when the request carries no header, so `deregisterDesktopConnection` can send `all` and `registerConnection` can name an organization other than the selected one. Calls that omit the argument behave as before. The logic moved to `typescript/rtk/currentOrgHeader.ts` (`CURRENT_ORG_KEY` is still exported from `api`), tested through a real `fetchBaseQuery` in `currentOrgHeader.test.ts`. No caller in meshery/meshery, layer5io/meshery-cloud or layer5labs/meshery-extensions passes the header explicitly today, so none changes behavior. Fixes #1355.

- **Desktop connections (v1beta3), contract**: `deregisterDesktopConnection` (`DELETE /api/integrations/connections/desktop/{installationId}`) takes an optional `X-Current-Orgid` header. With an organization id it deletes only the install's connection in that organization and leaves its connections in other organizations live, which is how an install releases the organization it is leaving on an organization switch; absent, or `all`, it deletes the install's connections in every organization, as before. Any other value answers `400`, and an organization where the caller has no connection for the install answers `404` (membership is not checked: a non-member with no connection there gets the same `404`, and a connection the caller still owns in an organization it has left is deleted). A token linked to a removed or superseded desktop connection (`metadata.tokenId`) is revoked only once no live connection of the same owner still links it, on deregistration, on `deleteConnection` and on a re-registration with a different token, so removing one organization's connection never signs the install out of another. Before this, a deregistration scoped to the old organization deleted the install's connection in the new one and revoked the sign-in it was using.

- **Errors (v1beta3), new construct**: `error` defines an error code's definition, `ErrorDefinition` (`code` = `<component.name>-<numericCode>`, `moniker`, `component` {`type`, `name`}, `numericCode` as digits, optional `severity` on MeshKit's ladder plus the lower event levels, `shortDescription`, `longDescription`, `referenceUrl`). Its `probableCauses[]` each carry `id`, `description` and `remediations[]`, and each remediation `id`, `description`, an optional `action` (for example `service.start`) and `actionPolicy` (`automatic`, `requiresApproval`, `manual`; an omitted policy means `manual`; `automatic` and `requiresApproval` need an `action`). A remediation shared by several causes is repeated under each with the same id. The flat `probableCause[]` / `suggestedRemediation[]` stay, derived from the nesting. `ErrorReferenceIndex` (`schemaVersion` 2, `errors[]`) is the docs.meshery.io `index.json` and MeshKit's per-component `*_errors_index.json`; the legacy `*_errors_export.json` is unchanged. No endpoints, no stored row. Go: `models/v1beta3/errorcode` (package `errorcode`), with `FlattenProbableCauses`, `ErrorDefinition.Validate` and `ErrorReferenceIndex.Validate`. TypeScript: `v1beta3.ErrorDefinition` and related types, plus `flattenProbableCauses`, `validateErrorDefinition`, `validateErrorReferenceIndex`, `validateEventError` and `effectiveActionPolicy`. Requested in #1334, with meshery/meshkit#1138 and meshery/meshery#22743. Contract: `docs/error-definition-contract.md`.

- **Events (v1beta3), additive**: new `EventError`, the `metadata.error` of an error event (`code`, `component`, `severity`, rendered descriptions, `probableCauses`, `matchedCauses[]` of `EventMatchedCause` {`causeId`, optional `confidence` from 0 to 1}, the flat lists, `referenceUrl`, `details`). An error with only flat lists stays valid and is unpaired. `Event.metadata` stays free-form. New optional fields on `EventPayload`, `Event` and `EventResult`: `correlationKey`, `occurrenceCount`, `firstSeenAt`, `lastSeenAt`, `resolvedAt` (condition correlation, meshery/meshery#20879), `source`, `type` and `specversion` (`"1.0"`; CloudEvents compatible), and `traceId` and `parentId` (W3C Trace Context, minted by clients). `createEvent` keeps its id and path and documents upsert by `correlationKey`. An `idempotencyKey` replay is checked first. A call that identifies no user records a new event and stores the correlation fields exactly as sent (no defaults, no matching). For a call that identifies a user, an open condition's occurrence is counted (`200`), which also advances `updatedAt`. A `resolvedAt` closes it without adding to `occurrenceCount`, copying `severity` and `description` only when the payload carries them (an omitted field keeps the stored value) and bringing `lastSeenAt` forward (`200`). A resolving create with no open condition is inserted already resolved (`occurrenceCount` 1 when omitted; `firstSeenAt` and `lastSeenAt` from the payload, else `resolvedAt`). `EventPayload` accepts optional `severity`, the same open string as `Event.severity`. Anything else records an event (`201`). A server may answer a legacy create (neither `correlationKey` nor `idempotencyKey`) with `200` and `Event-Disposition: created`; clients accept any 2xx and read the header. The new optional `Event-Disposition` response header says which happened (`created`, `replayed`, `incremented`, `resolved`). `getEvents` rows (`EventResult`) also carry optional `id`, `actedUpon`, `operationId`, `severity`, `status`, `metadata`, `updatedAt` and `deletedAt` (#1353). `EventResult.systemId` is marked `x-id-format: external`. Exported as `v1beta3.Event`, `v1beta3.EventPayload`, `v1beta3.EventError`, `v1beta3.EventMatchedCause`, `v1beta3.EventSpecVersion`; Go helpers `EventError.Validate`, `Paired` and `FlatLists`. Contract: `docs/event-correlation-contract.md`.

- **Design validation events (v1beta3), additive**: `DesignValidationEventMetadata.status` documents its values: `success`, `partial`, `failed` (the operation ran and found errors) and the new `error` (the operation did not complete, so there is no verdict). It stays an open string; consumers must tolerate unknown values. New optional `error` property of the new closed `DesignEventOperationError` shape (`code` required: the MeshKit error code, otherwise a producer code such as `validator-exception` or `validator-no-result`; optional one-line `message`, never design contents), present only when `status` is `error`. With `status` `error`, `errors` is empty or omitted, `errorCount` and `truncated` are omitted, the identity fields are kept, and the event is recorded as category `pattern`, action `validate`, severity `error`. Exported as `v1beta3.DesignEventOperationError`. Requested by layer5labs/meshery-extensions#4401 (#1341). Contract: `docs/design-event-metadata-contract.md`.

- **Registry (v1beta1), typing fix**: `RegistryRelationshipsPage.relationships` items now reference the v1alpha3 `RelationshipDefinition` schema instead of the whole v1alpha3 `relationship.yaml` OpenAPI document. The 200 bodies of `GET /api/registry/relationships`, `GET /api/registry/models/{model}/relationships` and `GET /api/registry/models/{model}/relationships/{name}` now type `relationships` as relationship definitions instead of `unknown[]`, and the bundled specs and `RegistrySchema.ts` no longer embed copies of that document. No wire change. New blocking validator Rule 48 rejects any `$ref` with no fragment whose target is an OpenAPI document, and any remote `$ref` with no fragment, in the `api.yml`, entity schemas and helper `.yml` files of every non-deprecated construct version. A new bundle guard, `tests/bundled-openapi-documents.test.js` (run by `make test-rtk`), fails if a generated bundle still carries an OpenAPI document where a schema belongs (meshery/schemas#1304).

- **OAuth consent requests (v1beta3), new construct**: cloud-only `oauth_consent_request` backs the consent page for dynamically registered OAuth clients. `getOauthConsentRequest` (`GET /api/identity/oauth/consent-requests?consentChallenge=...`) answers the pending `OauthConsentRequest` (`consentChallenge`, `client`, `requestedScopes`), whose `OauthConsentClient` names the client (`clientId`, `clientName`), where it can send the user in two deduplicated lists that are never both empty (`redirectHosts`, the network hosts of its https and loopback redirects, in IDNA A-label (punycode) form; `appSchemes`, the private-use schemes of its app redirects, so an app is never shown as a host; registration accepts a private-use scheme only when it is on the server-side app-scheme allowlist read from configuration, defaults `vscode` and `cursor`, so `appSchemes` only ever holds allowlisted schemes) and the `verified` mark, the only trust mark, derived only from the client's redirect targets and never from `clientName` or `clientId`: it is true only when every redirect URI of the client matches one operator-listed known-client entry (its https hosts or its app schemes). `acceptOauthConsentRequest` and `rejectOauthConsentRequest` (`POST .../accept`, `POST .../reject`) take `OauthConsentDecisionPayload` (`consentChallenge`, optional `remember`, default `false`) and answer `OauthConsentRedirect` (`redirectTo`), which the browser must navigate to. Only the signed-in user the challenge was issued for may read or decide it (`403`), a challenge is single use (`404` once decided or expired), an accept grants only what the client requested, and `verified` marks trust and never blocks. Refusals `400`, `403`, `404`, `500` and `503` (identity provider unreachable; on a decision the outcome is unknown, and a retry that answers `404` means it was already decided) carry the MeshKit JSON error body. The decisions are tagged `oauthConsentDecisions`, apart from the read's `oauthConsentRequests`, so the generated RTK client does not refetch the consumed challenge after a decision. Contract: `docs/oauth-consent-request-contract.md`.

- **Tokens (v1beta3), additive**: defines the token and session routes Meshery Cloud already serves on its bare router: `revokeToken` (`POST /revoke`, body `TokenPayload`) revokes an OAuth access or refresh token issued by the identity provider or a user-created API token; a token issued to a third-party OAuth client ends that user's whole grant to that client, and any other OAuth token is forwarded to RFC 7009, revoking it and the tokens issued alongside it from the same authorization. It answers `200` (also for an unknown or already-revoked token), `400`, `500` when the revocation call itself fails, or `503` when signing keys or the token store are unavailable or the OAuth2 server cannot be asked who the token belongs to, and the caller should retry. `introspectToken` (`POST /introspect`, body `TokenIntrospectionPayload`: `token` and an optional RFC 8707 `resource` naming the protected resource asking, default the REST API) checks an access token for that resource: `200` with a `TokenIntrospection` body (`active`, `aud` always a JSON array, never null, and the RFC 7662 members `sub`, `clientId`, `scope`, `exp`, `iat`, `nbf`, `iss`, `tokenType`); `400` for a malformed or empty body, or `invalid_target` for a resource the server does not issue tokens for; `401` for an invalid or revoked token or one whose audience does not include the resource - deliberately a `401` rather than RFC 7662's `200` with `active: false`, as this is the server's status API; or `503` when it cannot be checked and the caller should retry. Both take `security: []`; `logoutUser` (`GET /logout`) signs a browser out through the new `sessionCookie` and `providerTokenCookie` cookie security schemes, answering `303` or `302` to `/login`, or an empty `500`. See `docs/http-api-design.md`.

- **Bundler, route ownership (`x-supersedes`)**: a newer construct version can take over a route from an older one by setting the operation extension `x-supersedes: <older version>` on its declaration. The collision resolves to the owner only when both declarations are the same construct, their `operationId`s match, their `x-internal` targets match, the owner names exactly the other declaration's version, and the superseded declaration carries no `x-supersedes`. The owner may use `$ref` in its `api.yml`; the merge fails if the bundled (dereferenced) owner still holds one. The owner's `x-supersedes` must also name a declaration of the same route, or the merge fails with `x-supersedes names no declaration`; an owner that names its own version, a newer one, or a string that is not a construct version fails with `which is not older than` (versions order by major, then alpha, beta and GA, then number). Any other duplicate still fails the build with `Duplicate path operation during merge`. The bundler owns and checks the rule; the consumer endpoint index walks each construct's latest non-deprecated version, so it indexes the owner's declaration once while the owner is that version, and has no ownership logic. `updateUserPreferences` (`PUT /api/identity/users/preferences`) moves to v1beta3 user under this rule: the route keeps its method, path, `operationId` and `x-internal`, and its body is the v1beta3 `PreferencePayload`, so the generated clients pick up the optional, nullable `agentsActWithoutApproval` when master regenerates them (the merged cloud client's request type, `typescript/rtk/cloud.ts` `UpdateUserPreferencesApiArg`, is not regenerated in this change). v1beta2 user keeps its declaration, so the v1beta2 generated types are unchanged, and code importing those directly needs no change. The extension stays in the merged output, as `x-internal` does. See `docs/http-api-design.md` (Route ownership across versions).

- **Hosted auth shapes (v1beta3), write rules**: `PreferencePayload.agentsActWithoutApproval` is nullable, and its Go type is `nullable.Nullable[bool]` (`github.com/oapi-codegen/nullable`), so a Go client can send `true`, `false`, `null` (clears it) or leave the key out (keeps it). On `updateUserPreferences` it has three states: `true` or `false` stores that value, `null` clears it back to absent (inherit), and an omitted key keeps the stored value. `Preference` reads absent as not set. Once the typed field has been written (any accepted write from the signed-in session that names it, `null` included), the server never again reads the free-form `remoteProviderPreferences.<provider>.agentsActWithoutApproval` value, and `null` means inherit, not that value. A request authenticated by an API token, of any kind (a token issued to an OAuth client or MCP app, or a personal API token from `generateToken`), cannot change `agentsActWithoutApproval`; only the signed-in session can. The discriminator is the authentication (token or session), not `isOauth` or scopes. A token-authenticated payload that names `agentsActWithoutApproval`, with any value including `null`, is answered `403` and no part of it is applied; only the signed-in session can set it. The same `403` applies when a token-authenticated request would change the stored state of a `remoteProviderPreferences.<provider>.agentsActWithoutApproval` entry (a different value, adding it where absent, or removing it where present); writing back the stored entry unchanged is accepted. The merged spec declares that `403` on the route, which v1beta3 user owns; see `docs/agent-approval-preference.md` (Where the route is declared). A re-consent that changes scopes changes the client's existing tokens (`OauthConsent` requires at least one keychain scope, and a re-consent that leaves none revokes the consent and its tokens); the rule is stated in `docs/oauth-consent-contract.md` and the `OauthConsent` schema description. A re-consent keeps the consent's `organizationId` unless the user explicitly chooses another organization; that move revokes every token the client holds for the user, and tokens are never re-bound silently. Contracts: `docs/agent-approval-preference.md`, `docs/oauth-consent-contract.md`, `docs/token-scoping-contract.md`.

- **Hosted server auth shapes (v1beta3), additive**: `UserToken` gains optional `keychainIds` (the keychains a token is limited to; a token is unrestricted only when `keychainScoped` is false or absent and `keychainIds` is empty or absent, a non-empty list always makes the token scoped, and a scoped token with an empty list holds no keys; existing unrestricted tokens are unchanged) and `expiresAt` (absent never expires), settable through the new optional `TokenCreatePayload` body of `generateToken`. `UserToken` also gains read-only `keychainScoped` (db `keychain_scoped`), the server's stored record that a token is keychain-limited, set at creation and changed only from false to true when a re-consent narrows an unrestricted token; it is never reset to false, and a non-empty set of keychain mappings always means scoped too (the stored flag OR any live mapping), so a scoped token whose keychains are all deleted holds no keys. New `TokenStanding` schema (no operation): the server-side read result of looking up a token by `jti`, with `id`, `revoked`, `expired` and `keychainScoped`. New `oauth_consent` construct: `getOauthConsents` (`GET /api/identity/oauth/consents`, core `page` and a consent-specific `pageSize` bounded to 1..1000, `400` when out of range) lists the signed-in user's live consented OAuth clients (session only; a token-authenticated call answers `403`) as an `OauthConsentPage` of `OauthConsent`, and `deleteOauthConsent` (`DELETE`, required `clientId` query, `204`, `403`, `404`) revokes one client's consent and tokens: a session may revoke any of the user's consents, a token only the consent of the client it was issued to, and a personal API token none. `OauthConsent` carries a server-generated `id`, a server-set read-only `updatedAt` (db `updated_at`) and a soft-delete `deletedAt` (db `deleted_at`, set on revoke); `clientId` is unique per user among live consents, and a re-consent by the same user to a live client updates that consent in place (replaces `scopes`, advances `updatedAt`, keeps `id`, `createdAt` and `organizationId`, unless the user explicitly chooses another organization, which also revokes the client's tokens). `Preference` (v1beta3 user) gains optional `agentsActWithoutApproval`, writable through the v1beta3 `PreferencePayload`. Interim rule (temporary, until the upstream platform, workspace and profile policies exist): `inherit` (including absent) resolves to `required`, whatever `agentsActWithoutApproval` says. During the interim the preference is stored and writable but is not consulted by approval resolution; it becomes the profile-level source once the hierarchy places that level. The interim does not wait on the hierarchy proposal. Target model, once the hierarchy places the profile level: it is one profile-level source in the approval hierarchy (platform, workspace, profile), consulted only for an AI-app write whose activity `approvalPolicy` (`required`, `not_required` or `inherit`; no schema default, and absent behaves like `inherit`) inherits, and only if no higher-level setting has already decided. `true` resolves to `not_required`, `false` to `required`, and absent sets nothing. An explicit `required` or `not_required` on the activity always wins. With nothing setting a value, approval is required (fail closed). The hierarchy and this fallback are open in https://github.com/layer5io/meshery-cloud/issues/6365. `updateUserPreferences` (`PUT /api/identity/users/preferences`) is still declared by v1beta2 user, unchanged, and is owned by v1beta3 user: the v1beta3 operation takes the v1beta3 `PreferencePayload` (with `agentsActWithoutApproval`) as its request body and declares the `403` for token-authenticated writes of it. The merged spec declares the route once, as v1beta3 owns it. Once the typed field has been written, the free-form `remoteProviderPreferences.<provider>.agentsActWithoutApproval` value is never read again. Contracts: `docs/token-scoping-contract.md`, `docs/oauth-consent-contract.md`, `docs/agent-approval-preference.md`. A request authenticated with a keychain-scoped token cannot create tokens: `generateToken`, `issueIndefiniteLifetimeToken` and `getNativeClientAuthorization` answer `403` and mint nothing (see `docs/token-scoping-contract.md`, Token creation).

## v1.1.0 — Phase 1 of the identifier-naming migration

Marks the completion of Phase 1 of the [identifier-naming migration](docs/identifier-naming-migration.md).
Phase 1 is governance- and tooling-only: no wire-format changes are made in this release.
The validator, advisory baseline, CI jobs, and docs have been realigned so that every
subsequent per-resource rollout (Phase 2 non-breaking alignment, Phase 3 versioned migrations)
has a single source of truth and a single rule surface to reason against.

### The canonical-casing contract

In one sentence: *wire is camelCase everywhere; DB is snake_case; Go fields follow Go
idiom; the ORM layer is the sole translation boundary.* Concretely, every JSON tag and
every OpenAPI schema property — DB-backed or not — is camelCase; the snake_case DB
column name lives only in `x-oapi-codegen-extra-tags.db`. URL path and query parameters
are camelCase with an `Id` suffix (`{orgId}`, `?userId=...`). The earlier conditional
rule "JSON tag matches `db:` tag when the field is DB-backed" has been retired. Legacy
resources retain their published wire casing until their next API-version bump; new
API versions adopt the canonical contract uniformly.

See [`docs/identifier-naming-migration.md` §1](docs/identifier-naming-migration.md) for
the full contract table and [`AGENTS.md` § Casing rules at a glance](AGENTS.md) for the
per-layer rules enforced by the validator.

### Phase 1 landings

- **1.A — `AGENTS.md` identifier-naming amendment** (#788): Replaced the "DB-backed =
  snake on the wire" rule with the canonical camelCase-on-wire contract; converted
  `page_size` / `total_count` from a perpetual exception to a deprecation list; added
  `§ Identifier-naming migration` pointing at the executable plan.
- **1.B — Rule 6 inversion / Rule 32 retirement** (#791): Rewrote the schema-property
  casing rule to require camelCase unconditionally; removed the DB-backing exception
  path and retired the superseded rule that enforced snake-on-DB-backed tags.
- **1.C — "Partial casing migrations forbidden" rule (Rule 45)** (#792): New rule
  walks every `components/schemas/<Entity>` and fails any struct that mixes JSON-tag
  conventions across its properties (camel + snake + `ID`). Catches the
  `OrgID`/`workspace_id`/`user_id` drift class on a single struct.
- **1.D — "Sibling-endpoint parameter parity" rule (Rule 46)** (#793): New rule
  flags `GET /api/<entity>` siblings that omit `orgIdQuery` when their peers declare
  it — the class of drift that produced the workspaces-400 incident.
- **1.E — Query-parameter casing (Rule 4 extension)** (#794): Extended the path-param
  casing rule to query parameters so `user_id`, `organizationId`, and any `orgID` that
  slips into `parameters: [{in: query}]` is flagged at the same severity as path
  parameters.
- **1.F — TypeScript consumer auditor** (#795): Added `validation/consumer_ts.go` and
  wired it into `make consumer-audit`. Parses RTK Query `builder.query` /
  `builder.mutation` call sites across `meshery/meshery/ui`, `meshery-cloud/ui`, and
  `meshery-extensions/meshmap` and reports three finding classes (`case-flip`,
  `snake-case-wrapper`, `snake-case-param`) against the schemas endpoint index.
- **1.G — Advisory baseline refresh** (#796): Regenerated
  `build/validate-schemas.advisory-baseline.txt` against the new rule surface so the
  `advisory-audit` CI job stays green while Phases 2–3 migrate each resource. The
  baseline is subtractive — any *new* violation introduced after this snapshot blocks
  CI.
- **1.H — CI workflow wiring** (#797): Adds a non-blocking `consumer-audit` job to
  `.github/workflows/schema-audit.yml` that checks out the downstream repos and runs
  `make consumer-audit` on every PR, posting divergence counts per downstream repo.
  Advisory-only; lands alongside this 1.I release.

### Dependency on this version

Every Phase 2 agent pins its target repo's `@meshery/schemas` dependency to this
version — no Phase 2 PR runs until this release is available on npm and as a Go module
tag. The Phase 3 per-resource rollouts (22 resources in parallel) likewise depend on
consumers reaching this version. Downstream repositories pin as follows:

```sh
# TypeScript / npm consumers (meshery, meshery-cloud, meshery-extensions UI):
npm install @meshery/schemas@1.1.0

# Go module consumers (meshery server, meshery-cloud server):
go mod edit -require github.com/meshery/schemas@v1.1.0
go mod tidy
```

After merging this release, downstream repos can begin Phase 2 non-breaking alignment
work (handler query-param casing, outbound URL alignment, local-type displacement) and
Phase 3 per-resource API-version authoring. See the [orchestration DAG in §11 of the
plan](docs/identifier-naming-migration.md) for the dependency ordering.

### Breaking changes

None. Phase 1 is a governance and tooling release; all wire contracts published in
prior releases remain accepted. Existing `json:"snake_case"` tags on DB-backed fields
in already-published API versions remain valid until their resource is migrated to a
new API version under Phase 3.
